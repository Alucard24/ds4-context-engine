# Release 0.4.9 — Compaction preparation performance and attribution

**Coordinated packages:** `ds4-context-core`, `ds4-context-reference-adapter`, and `ds4-context-engine` 0.4.9.

## Changes

- The Pi compaction adapter indexes each canonical message fingerprint once and consumes matching entry IDs in source order, instead of searching and re-serializing earlier candidates for every message. Exact canonical matching and fail-closed behavior on missing messages remain unchanged.
- Compaction diagnostics report non-overlapping local preparation, generation, aggregation and persistence wall times. Preparation is split into index sync, source mapping, prompt planning and segment planning. Index sync additionally reports its nested canonical JSONL and semantic sync durations (not to be added twice). The latest diagnostics appear in `/context compaction` and metadata-only `compaction.timings` logs, including when in-process summary generation fails.
- A summary halted by the provider's output limit reports whether the failed stage was `segment`, `aggregate` or `update`. This is a diagnostic change, not an automatic increase of output budgets or a guarantee that Pi's fallback succeeds.
- Adds synthetic adapter, runtime and coordinator tests and `tests/benchmarks/compaction-preparation.bench.ts`; the benchmark uses a local fake provider and logs only counts and timings when explicitly requested.

## Scope and limitations

The real report that motivated this work showed roughly 1,131 seconds of local preparation within a 1,268-second operation, followed by an output-limit failure. The prior report did not divide preparation among indexing, source mapping and segmentation. A synthetic 1,283-message case measured about 208 ms preparation (about 183 ms segment planning and 23 ms source mapping) with a no-op index sync. This one-sample result neither reproduces nor explains the real delay. The 0.4.9 diagnostics are needed on the affected host before attributing that delay or claiming it resolved. No live provider run was made for these changes. BPE/auto-tuning defaults and compaction validation policy remain unchanged.
